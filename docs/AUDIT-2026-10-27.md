### 2.2 建议补充的功能

**P0 —— 补的是"已有功能的证据缺口"，不是新功能**

1. **用真实整合包跑一遍 `--pack`**（成本 1 小时）
   拿一个真实 mods 目录，把 `unreadable` / `undecided` 逐条看完；至少把 3 个真实 jar
   压成最小 fixture（可脱敏）进测试。验证方式：`--pack` 输出的 unreadable 比例，
   以及"认不出"是否被显式列出——这条是 2.2 的硬要求。
2. **读 Fabric `environment` 字段 → `pack.client-mod-on-server`**（成本半天）
   影响 `manifest.py` 及其 28 项测试。验证：合成 jar + 真实 jar 各一，且缺字段时
   仍然输出 NOT CHECKED 而不是猜。
3. **`other` 桶下一条规则**（成本 1–2 天）
   先按 description + 根因 kind 聚类其余 `other` 报告，挑最大一簇写规则；命中 n≥30 才计入
   公开比率。风险：规则写宽了会把 `mod-bug` 抢成 `other`——用现有分桶断言挡住。

**P1 —— 差异化功能，成本低、别人没做**

4. **崩溃指纹与批量聚类**：同一崩溃的 N 份日志合成一条结论 + 计数。

   指纹过粗会合并不同问题，必须同时输出簇内差异。验证：454 份上跑，报告平均簇大小

### 3.3 审计中发现并修复的功能缺陷（`e6a1367`）

这一条比清理本身重要，单列出来。

**现象**：`mcd/rules/engine.py` 没有 schema，`Rule.from_dict` 只读它认识的键，其余静默
忽略。所以：

| 写错的地方 | 实际后果（实测 `tmp/unknown_key_probe.py`） |
|---|---|
| `when: {exceptions: [...]}` | 规则在我全部 4 份合成 fixture 上触发，包括**没有 OOM 的报告** |
| `fix: [...]`（少个 s） | 规则正常触发，修复步骤 **0 条** |
| `explaination:` | 规则触发，`explanation` 为空串 |

**为什么 `exceptions:` 会变成"匹配一切"**：`evaluate_rule` 开头只判 `if not w: return None`。
键名全拼错时 `w` 是非空 dict，空判据通不过，而里面没有任何一条引擎认识的约束——于是
一条条件都没有，全部 `need()` 返回 True。**这不是"永不触发的死规则"，是"每份报告都
误报的活规则"**，而 `RuleSet.errors` 是空的。

**修法（两层，因为错在两处产生伤害）**：
- **加载期**：新增 `RULE_KEYS` + `_config_warnings()`，把未识别的顶层键与 `when` 键
  记进 `RuleSet.errors`（CLI 打到 stderr，`--strict` 升级为错误）。只警告不拒绝——
  为一个拼写错误去打断用户正在用的规则目录是错的取舍，与既有 `WHEN_KEYS` 的判断一致。
- **求值期**：`when` 里没有任何引擎认识的键时直接 `return None`，与空 `when` 同义。
  理由：stderr 警告救不了库调用方，他们根本看不到；而它产出的 finding 在每份报告上
  都是错的。
- 顺带：`rules:` 下写一个字符串（`- just a string`）原来抛 `AttributeError` 逃出
  单规则异常处理器（不在它的 except 元组里），整个加载挂掉；现在只记一条警告。

12 项回归测试（`tests/test_rule_config_warnings.py`），含**反向对照**（拼写正确的规则
仍然触发）与**部分拼错**（好条件不能被连坐）。
产物规则：内置 41 条 0 警告（当时），语料 655 份 0 差异。
