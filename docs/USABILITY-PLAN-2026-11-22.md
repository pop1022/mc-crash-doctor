# mc-crash-doctor：从工程 Alpha 到可交给玩家的版本

2026-11-22｜实施负责人：CodeBuddy｜范围：本目录下的独立仓库，不含外层 demo。本文件是执行方案，不是完工记录。预算是单人粗估，性能和试用数字是建议验收线，不是已有成绩。

## 目标：三个人拿到它之后能做什么

| 用户 | 交付体验 | 建议验收 |
|---|---|---|
| 第一次崩溃的玩家 | 不装 Python、不上传日志；能找到文件，看懂原因，尝试一个可逆操作，知道如何判断有没有修好 | 找 5 位未用过本工具的人，至少 4 位无需指导在 2 分钟内从打开网页走到说出正确下一步；逐例记卡点，不把这当总体成功率统计 |
| 服主 | 在服务器副本上只读检查；分清“已声明冲突”“可能相关”“不知道”；能复制脱敏摘要求助 | 可启动整合包、已知缺依赖包、无法读取的 jar 各一份；无错拦、能定位证据、不修改服端文件 |
| 整合包维护者 | 从干净环境装上发布物，按固定版本在 CI 跑；知道哪些证据值得拦 PR | 从 wheel 和 sdist 各做一次中性目录安装；示例仓一次坏包拦截、一次软提示放行；产物和测试指向同一 SHA |

## 调研为什么改变优先级

- [Fabric 崩溃报告](https://docs.fabricmc.net/players/troubleshooting/crash-reports)、[Modrinth 日志指南](https://support.modrinth.com/en/articles/9005261-minecraft-logs)、[Prism Launcher](https://prismlauncher.org/about/)：日志位于具体游戏实例，不一定是系统默认目录；JVM 崩溃日志还可能带启动凭证。**先解决拿错文件和误分享**，不是先加一个上传入口。
- [mclo.gs](https://github.com/aternosorg/mclogs-integration) 已有分享流程，[Crash Assistant](https://modrinth.com/mod/crash-assistant) 已有崩后收集入口。我们的差异应是**无需装模组、不上传也能诊断、给出可查证的下一步**，而不是再做一个日志托管站。
- [Fabric 清单规范](https://wiki.fabricmc.net/documentation:fabric_mod_json) 与 [NeoForge Mod Files](https://docs.neoforged.net/docs/gettingstarted/modfiles/) 区分导致加载失败的依赖和仅警告的依赖。[Modrinth 批量哈希查询](https://docs.modrinth.com/api/operations/versionsfromhashes/) 可补充文件身份，不能证明两个模组互相致崩。
- [Pyodide Worker 指南（本项目固定版本 0.26.4）](https://pyodide.org/en/0.26.4/usage/webworker.html)、[W3C 状态消息](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)、[Playwright 网络测试](https://playwright.dev/docs/network)：分别解决分析阻塞界面、读屏获知进度、可重复验证断网和隐私承诺。Worker 不会减少首次下载量。
- [PyPA 发布指南](https://packaging.python.org/en/latest/guides/publishing-package-distribution-releases-using-github-actions-ci-cd-workflows/)、[PyPI 首次发布](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/)、[GitHub Actions 上下文](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)：构建、测试、授权上传分开；分支演练不等同于标签发布，也不能证明 PyPI 已授信。

## 工作顺序与完成标准

### P0：建立可信的候选版本（估 2–4 人日，公开发布前必做）

1. **固定比较对象。** 本地 `b88dca6` 比公开 `41f3fcc` 多 24 个提交，另有大量未提交改动。先记下 SHA、`git status` 和差异清单；在现有工作副本上增量修改。用单独临时目录或 CI 工件验证候选文件集合（含拟交付的未跟踪文件），不要用“只含 HEAD 的干净副本”冒充候选，也不要顺手提交私人语料。公开 [CI 失败运行](https://github.com/pop1022/mc-crash-doctor/actions/runs/40190281816) 的 3 个 Python 版本均停于 pytest；取具体失败用例，分开验证夹具缺失、平台差异与候选上仍存的问题，不预设根因。
2. **修发布链，不实际发布。** 查 `.github/workflows/{tests,release,publish}.yml`。分支 dispatch 只能演练，不比较分支名与包版本、永不上传；正式发布只能来自匹配包版本的标签、受保护 environment、最小权限。避免 Release 与 PyPI 分别重建不同产物；测试同一构建的 sdist、wheel，记 SHA256。修复 `release.yml` 中空 venv 使用 `--no-deps` 漏装 PyYAML；在源码目录之外验证导入位置、46 条规则（最终从清单读取期望）、诊断 fixture、pack、JSON。覆盖分支演练、正确标签、错误标签三条路径。没有远端授权就记录待核验，不宣布远端已绿。
3. **让数字可重建。** 默认 pytest 1193 过、1 跳过；开启 `MCD_DRIFT_FULL=1` 后，候选报告旧值 110/454 未覆盖、现场重算 106/454。先对齐语料清单、规则版本、分桶口径，再从生产脚本重建相互依赖的 JSON/Markdown；不要直接把 110 改成 106。连续生成两次应无实质差异。区分公开脱敏 fixture 的 PR 门禁与需私有语料的扩展门禁，后者缺数据时显式标“未运行”；不能靠静默 skip 变绿。让 CI 真正执行承诺的 lint、覆盖率、契约、产物一致性检查；先本机、再同 SHA Linux 声明版本矩阵及 Windows 烟测。
4. **修正产品承诺。** `157/214` 是盲测规则命中，`112/143` 是模组仓规则命中；均非“猜对模组”。可计分归因只有 7 例（5 对、1 错、1 不选）。网页、两份 README、assessment、发布清单统一从机器数据取值或指向它；示例里未经校准的“97%”不能被呈现成正确概率，优先显示证据强弱。验收：抓一条旧的错标文案能让语义检查或审阅清单报警；记录本次实际执行、跳过和失败的检查。

### P1：让玩家第一次就能用（估 3–5 人日，优先于扩规则）

5. **输入和输出沿玩家的顺序排。** 在 `web/src/`、README 和 CLI 帮助补齐缺口，不重做已有拖放、预生成示例、双语译文和反馈按钮。首页以“刚崩了，去哪找文件？”为入口：当前实例 → 最新 `crash-reports/*.txt` → 没有则 `logs/latest.log`；给默认启动器、Prism、Modrinth 和服务端入口。粘贴退出码、裸链接、空文件、过大日志、JVM `hs_err` 各给明确下一步，不静默上传或假装能解析。结果依次是：**发现了什么 → 依据哪一行 → 先做什么 → 如何验证/撤回**。未命中、并列、只有共现时给补充材料指引，不默认让用户删模组、改世界或盲目加内存。用缺前置、watchdog、未知故障三份 fixture 检查中英结果；机器 JSON 保持兼容。
6. **把“秒出示例”和真实速度分开测。** 用 `performance` 记录冷启动、热启动、示例显示与真实文件诊断四项，在同一设备/输入/网络档位重复跑并报告中位数和慢端，不使用虚构性能数字。固定中档机测试：示例点击后目标 ≤1 秒；弱网启动不吞输入并有重试/CLI 退路；大日志运行时仍能取消或重新选择。在 `web/src/20-engine.js` 先量主线程阻塞，再按 0.26.4 说明将重计算移入 Worker；不为 Worker 强制升级整个技术栈。CDN 全断时预生成示例必须标“示例”，用户报告必须明确未分析。若冷加载仍主导失败，再评估同源自托管固定版本（包含运行时及实际依赖、校验值和体积预算），不要把镜像轮询写成完全离线。
7. **隐私和可访问性以行为验收。** 在现有真浏览器脚本上扩展，或用 Playwright；无需为选框架重写测试。构造仅测试用的路径、IP、令牌标记，断言原始日志和标记不进外部请求、URL、持久化存储或公开 issue。反馈先给脱敏预览，用户主动确认才离开页面，不自动发帖；只记录汇总默认不做遥测。测键盘全流程、窄屏、语言切换、读屏状态播报、重试和 CDN 全断。对未支持的原生崩溃日志尤其提示勿公开整份文件。

### P2：证明建议有用，而不只是规则命中（估 3–6 人日搭建；积累样本另计）

8. **建立小而可信的反馈集。** 复用 `--feedback`、issue 模板、`tools/ingest_feedback.py`；分开记录错模组、错根因、没命中、修复是否有效及证据来源。默认不收原日志；仅经同意、脱敏、许可检查后纳入。新增样本按 issue/近重复簇分组，开发与留出集不得交叉；按加载器、故障族报告命中率、弃答、错指、修复验证的分子/分母和区间。目标先取得 ≥40 个可核对方向的独立案例；不足时报计数，**不能用命中率或回归测试数代替**。新增规则需真实正例与相似负例；优先修重复出现且有明确下一步的问题，而非按覆盖率堆规则。
9. **让 Pack / Server / CI 对同一证据说同样的话。** `depends/breaks` 与 `conflicts`、`incompatible` 与 `discouraged` 分级对照，加版本、侧别、嵌套包、无法识别的反例；优先补已有测试没覆盖的组合。硬声明可拦 PR、软警告不拦、证据不足单列。8,731 对只有共现的模组不得升为冲突判定；需要在线补全时才选择性启用 Modrinth 批量哈希、缓存与超时，明示传送哈希，默认纯离线。`--server` 标出扫描目录、日志时间和局限，`--watch` 不许承诺预测崩溃。对真实可启动包和已知坏包回放；记录残留误报与不确定项，不把“零报告”叫作“兼容”。

### P3：小范围试用后再发（1–2 人日准备；外部动作须人工）

10. **交付物与退出条件。** 准备玩家一页入门、服主检查示例、维护者固定版本 Action 示例、已知不支持列表、回退步骤和候选验证记录。公开页面显示引擎/规则版本方便反馈；线上与 CLI 对同一 fixture 核心字段一致。按开头三条用户路径试用，问题注明影响、复现与是否阻断发布。P0/P1 未过不可把候选称为正式版；P2 数据量不足可发明确限制的试用版，不宣传归因正确率。真实用户未招到就交付任务脚本与记录表，不伪造结果。

**暂不做：** 云端上传后分析、自动改服/删模组、全生态兼容数据库、桌面壳、编辑器扩展和远程监控。这些都不能替代前三条体验。仅当试用数据表明首要阻碍发生变化时重排。

## CodeBuddy 交接要求

从 P0 开始实际修改、测试，然后连续推进 P1、P2、P3 可在本机完成的工作；不要只提交另一份计划。阶段记录写 `docs/USABILITY-PROGRESS.md`，逐项记：变动文件、命令、输入、结果、剩余限制；不要把文档或静态测试当真实用户试用。保留现有未提交改动，不 reset/clean、不替用户提交、推送、打 tag、发布、配置凭证或上传私人日志。遇到仅需授权/用户的事项，列为单独人工清单，继续其余可做项。首个交付物应是可重复的候选验证、修好的发布演练和同步的评测产物，而不是改首页配色。
