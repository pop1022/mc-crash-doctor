## 1. 结论先行

四条判断，按对项目的冲击力排序：

**J1（已实测修正，见 §3.6）：声明式边存在但稀疏，只能做确认层，不能做骨架。**
生态里确实有机器可读的**声明式负向边**：Modrinth API 的
`dependency_type: incompatible`、Fabric `fabric.mod.json` 的
`conflicts` / `breaks`、Forge/NeoForge `mods.toml` 的 `type = "incompatible"`。
这些是作者本人写的"这两个装一起会炸"，属于**先验知识**。
`[事实]` `[置信度: 高]` `[状态: 已核文档]`

但 2026-10-21 的 1D.0 实测推翻了我原先"用它替代共现"的判断：
**71 条声明依赖里只有 5 条是 `incompatible`（7%），25 个抽样项目里只有
3 个声明过任何不兼容（12%）**。`[事实]` `[置信度: 中]`
`[状态: 已实测: corpus/MODRINTH_MAPPING.md]`

→ 结论（修正后）：声明式边的正确位置是**高精度、低召回的确认层**
（co-occurrence 出候选 → 声明式边确认或否决），而不是兼容图的骨架。
骨架仍是我们自己带维护者标注的语料。

**J2. "诊断率 65%"不是缺陷，是必须先公布的产品参数。**
文献一致显示：日志解析没有近乎完美的方案，且性能跨数据集漂移剧烈
（LogBase 上 LILAC 的 PA 从 0.84 掉到 0.56，LogPPT 从 0.76 掉到 0.57）。
`[事实]` `[置信度: 高]` `[状态: 二手转述: 综述级检索结果]`
→ 结论：不能等"更准的规则"，要把"未覆盖"做成**一等公民状态**并**量化公布**。
现有 `No rule matched this report` 路径方向是对的，但它现在是免责声明，
应该变成**可统计的覆盖率指标**。

**J3. LLM 不该进运行时，该进"知识生产线"。**
LLM4Log 综述点明三个未解挑战：漂移与长尾下的鲁棒性、面向运维输出的
grounding/faithfulness、可验证行为的部署设计。`[事实]` `[置信度: 中]`
`[状态: 二手转述]` 同时 LPB-Gen 这条线说明 LLM 在**离线生成解析模板/规则**
上是有产出的。`[推断]`
→ 结论：运行时保持确定性、离线、可审计；LLM 只进**离线语料标注与规则候选
生成**工具链，人在环。这恰好是数据飞轮转不动的真实瓶颈（人工写规则的成本）。

**J4. 我们的评测方法比业界主流更严，但样本量让结论没有统计意义。**
我们做的是确定性、方向感知、无 LLM 参与的盲测——而业界大量评测依赖
LLM-as-judge，且已被证明不可靠（21 个 judge、约 54.1 万次判断的审计发现：
原始一致率把 kappa 高估 33–41 个百分点，judge 排名跨基准最多移动 14 位）。
`[事实]` `[置信度: 中]` `[状态: 二手转述: 博客转述未核原文]`
→ 结论：评测路线正确，**别改**；但"7 份可计分样本、甩锅率 14%"必须
换成区间估计，且在 1C.2 对外发布前补到可支撑结论的样本量。

## 2. 方法与局限

**做了什么**：五轮定向检索，覆盖 (A) 日志解析与模板提取、(B) LLM 日志分析综述、
(C) 崩溃去重与工单分派、(D) 评测方法论、(E) MC 生态数据源与竞品。

**没做什么**，以及为什么这重要：

| 缺口 | 影响 | 缓解 |
|---|---|---|
| 无订阅数据库全文 | 可能漏掉非 arXiv 的 SE 顶会论文 | 引用只用于**方向判断**，不用于定量决策 |
| 未做系统综述协议（无 PRISMA、无双人筛选） | 有选择偏差 | 文末列出检索式，可复现 |
| 部分结论来自二手转述 | 数字可能失真 | 已标 `[状态: 二手转述]`，不进入验收标准 |
| 无 MC 领域专属文献 | 见 §2 末尾的元判断：这不是检索失败，是研究空白 | 该空白本身是可发表点 |

**一条元判断** `[推断]` `[置信度: 高]`：本项目的核心问题
（"第三方二进制生态里，谁该为这次崩溃负责"）在检索到的文献里**没有直接对应物**。
所有 log parsing / LLM4Log 工作都建立在"单一代码库产生的日志"假设上，
数据集是 HDFS、Spark、BGL、Thunderbird 这类**同质**服务器日志。
Minecraft 模组崩溃是**异质多方**问题：崩溃发生在 A 的代码里，根因在 B 的
字节码注入（mixin）、C 的版本约束、D 的注册表同步。这不是"日志分析"的子问题，
是"多方归因"问题。文献能借的是**方法**（评测、去重、置信度表达），
借不到**结论**（准确率、特征重要性）。

## 3. 文献图景：五条线

### 3.1 日志解析：精度天花板是结构性的

**关键结论**

- 没有解析器接近完美；性能**跨数据集剧烈漂移**，部署前必须在自己的日志上
  重新评估。`[事实]` `[置信度: 高]`（LPB-Gen, TOSEM）
- 基准本身偏窄：Loghub-2k 是 16 个数据集 × 2,000 行；LogBase 扩到
  130 个来源、85,300 个模板，结果**语义解析器集体掉点**：LILAC 的 PA
  0.84→0.56、FTA 0.81→0.42；LogPPT PA 0.76→0.57。
  `[事实]` `[置信度: 中]` `[状态: 二手转述]`
- 传统强基线依然能打：Drain3 在 LogBase 上 GA 0.89 / TS 0.81；
  LLM 系 Matryoshka 拿到 PGS 0.97 / TS 0.92，但代价是运行时 ≥3× Drain，
  且引入隐私面。`[事实]` `[置信度: 中]` `[状态: 二手转述]`
- "Preprocessing is All You Need" 用 15 条正则把 Drain 的 FTA 抬了 108.9%，
  但其自身的审稿意见指出：框架是从 Loghub 家族归纳、又在同一家族上评测的，
  且缺显著性检验。`[事实]` `[置信度: 中]` `[状态: 二手转述]`

**对本项目的意义** `[推断]` `[置信度: 高]`

1. **我们根本不做模板提取，这是有意的架构选择，不是能力缺失。**
   `mcd` 走的是"结构化字段抽取 + YAML 规则匹配"，不是"先聚类出模板再分类"。
   文献里所有精度争议都发生在模板层，我们绕过了那一层——代价是覆盖率靠规则
   手工扩，收益是**每条结论都能指回一条人能读的规则**。
2. **"跨数据集漂移"在我们这里表现为"跨版本漂移"。** MC 每年几个大版本、
   Forge→NeoForge 分裂、mixin 行为变化，等价于文献里的 distribution shift。
   所以 ROADMAP 2.3 的"版本回归对比"不是锦上添花，是**对抗漂移的必需品**，
   应该与 Pack Doctor 同期而不是之后。
3. **不要引入 LLM 解析器。** ≥3× 运行时、隐私面、掉点风险，换不到我们能用的
   东西——我们不需要"任意日志的通用解析"，我们需要"MC 报告的高精度字段抽取"。

### 3.2 LLM4Log：任务分类清楚，但落地挑战正好压在我们头上

**关键结论**（LLM4Log, TOSEM 2026, 145 篇）

- 任务分类：解析、异常检测、根因定位、摘要/报告生成。
- 设计范式五类：prompting/ICL、检索增强接地、微调、工具/Agent 增强、验证。
- 三个开放挑战：**漂移与长尾下的鲁棒性**、**面向运维输出的 grounding 与
  faithfulness**、**可验证行为的部署设计**。`[事实]` `[置信度: 中]`
- 争议：该综述的检索协议描述不足（Pith T0 评审，1 条主要反对意见）。
  `[事实]` `[置信度: 中]` `[状态: 二手转述]`

**对本项目的意义** `[推断]` `[置信度: 高]`

- 那两个挑战（鲁棒性、faithfulness）在 LLM 方案里是**未解难题**；
  在规则方案里它们是**已被结构性解决**的：规则不幻觉，因为规则不生成文本，
  只选模板；规则的每条断言都能追到 YAML 的 `when` 条件。
  **这构成一条清晰的产品主张**：不是"我们更准"，是"我们的每句话都能被审计"。
- 这也解释了一个竞品现象：mcdoctor.ai 承诺 15–60 秒出结果并要求上传日志
  （云端 LLM），而 mctoolbox.net 明确写"这是规则工具，不能证明栈里的模组就是
  元凶"。**两条路线都已经有人站住了**，见 §3.5。

### 3.3 崩溃去重与分派：解决的是"重复"，不是"归因"

**关键结论**

- `dedupT`（arXiv:2508.19449）：把栈迹整体建模而非孤立帧，PLM 适配 + FCN 排序；
  四个公开数据集上 MRR 比最强 DL 基线常超 15%，比传统方法最多高 9%。
  `[事实]` `[置信度: 中]` `[状态: 未核原文: 摘要级]`
- `TriagerX`（arXiv:2508.16860）：双 Transformer + 交互历史，开发者推荐
  Top-1/Top-3 常提升 >10%，已在工业伙伴部署。
- Khvorov 博士论文（Constructor University, 2025）：系统化栈迹去重/分组/分派，
  含工业级可扩展方案与"解释最有信息量的栈帧"的方法。
- 三者共同前提：**崩溃已经被采集、已经聚成组**，问题是"这条和那条是不是同一个 bug"
  以及"该派给谁"。`[推断]` `[置信度: 高]`

**对本项目的意义**

- **不适用**于我们的主问题。用户面对的是**单份**报告，要问"哪个模组害的、
  怎么修"，不是"这是不是重复工单"。
- **部分适用**于一个我们还没做但会需要的场景：`Mod Doctor`（ROADMAP 2.3）
  持续监控一个模组的 issue 流，必然面对大量重复报告。届时可借鉴的是
  **"解释最有信息量的栈帧"**（Khvorov 贡献 6）——这恰好是我们
  `W_FRAME_TOP=5` 加权在做的事，说明权重设计方向与文献一致。
- **明确记录一条边界**：文献里没有"从栈迹反推第三方二进制责任方"的方法。
  我们的四路加权（栈帧 2.5 / 顶层帧 5 / mixin 10 / jar 3 / 描述 1）
  是自建启发式，**没有文献背书**，只能靠盲测验证。这一点必须在
  README/文档里说清楚，不能借文献壮胆。

### 3.4 评测方法论：LLM-as-judge 的效度危机（我们的镜子）

**关键结论**

- `Bias in the Loop`（arXiv:2604.16790, Zhao/Esmaeili/Fard, 2026-04）：
  LLM judge 对 prompt 呈现线索高度敏感，即使被评代码未变；某些设置下
  足以**改变任务级结论与模型排名**；建议把 bias sensitivity 与 accuracy 并列报告。
  `[事实]` `[置信度: 中]`
- Berkeley 审计（21 judge / 9 provider / ~541,000 次判断，2026-06）：
  ① 原始一致率把 Cohen's kappa 高估 33–41 个百分点；
  ② 可重复性 ≠ 有效性——Qwen3-8B 与 Gemini-2.5-Flash 的 test-retest 可靠性
  超 0.95，同时存在严重位置偏差；
  ③ judge 排名跨基准最多移动 14 位。
  `[事实]` `[置信度: 低-中]` `[状态: 二手转述: 博客转述，未核原文]`
- 更早的 `Judging the Judges`（2025, 15 judge / >150,000 次比较）：
  位置偏差**不是随机噪声**，两个答案质量越接近偏差越大——恰是最需要正确判断时。
- `MetaQA`（Proc. ACM SE, 2025）：用蜕变关系 + prompt 变异做**无外部资源**的
  幻觉检测，优于 SelfCheckGPT。`[事实]` `[置信度: 中]`

**对本项目的意义** `[推断]` `[置信度: 高]`

1. **我们的盲测是这三篇论文推荐的形态**：无 LLM judge（消灭 judge 偏差）、
   确定性划分（可复现）、方向感知评分（避免把正确的外部归因算成甩锅）。
   这条路线不需要改。
2. **但要吸收两条具体做法**：
   - **区间估计**：Report 置信区间，不报点估计。现在"甩锅率 1/7 = 14%"
     的正确表述是 `1/7，Wilson 95% CI ≈ [2.6%, 39.9%]`——即"可能低到 3%，
     也可能高到 40%"。写 14% 是不诚实的精确。
   - **顺序稳定性测试**：Berkeley 的位置偏差提醒我们，即使确定性系统，
     "谁是 top-1"也可能被 tie-break 的微小参数左右。应加一条测试：
     把 top-1 与 top-2 的候选顺序人为交换后重算，结论不应翻转。
     这不是 LLM 专属问题，是**排序系统**的通用问题。
3. **MetaQA 的"无外部资源自检"思路可借用**：对同一条规则，
   改写报告中无关的干扰项（时间戳、玩家名、路径），诊断结论必须不变。
   这是**蜕变测试**，成本低，能抓住真实的过拟合。

而且他们做得不错（前端脱敏、明确写"不能证明栈里的模组就是元凶"）。
所以：

> **"我们是规则派、我们诚实"不再是差异化。差异化只能是三件事：**
> ① **无人在 CI/Action 里自动诊断 issue**（我们已有，1C.1）；
> ② **混合归因**（栈帧+mixin+jar+描述四路加权，不是单模式匹配）；
> ③ **可复现的量化指标 + 带维护者标签的语料**（没人公布准确率）。

这直接决定 §6 的优先级：**1C.1/1C.2 的对外发布必须先有 ② ③ 的支撑**，
否则就是把一个"和 mctoolbox 差不多但要多装 Python"的东西推出去。

### 3.6 实测：1D.0 的结果（2026-10-21）

> 这一节不是文献，是我们自己的测量。它的存在是因为 J1 的第一版是错的，
> 而错在一件本可以 30 分钟就查清的事情上：**我假设了声明式边会多**。
> 完整数据：`corpus/MODRINTH_MAPPING.md`；工具：`tools/audit_modrinth_mapping.py`。

**测了什么**：把 `corpus/index.jsonl` 里 488 份报告的模组标识（`jars` +
`mixin_configs`，共 765 个去重候选）按 sha256 序确定性抽 120 个，
用保守规则（只接受精确 slug 或归一化后完全相等的标题，无模糊接受）
去 Modrinth 匹配；再抽 25 个项目探其版本级依赖声明。

| 指标 | 结果 | 含义 |
|---|---|---|
| 模组候选匹配率 | **50.8%**（61/120） | 加词边界重试后；原始口径 45.8%，剔除前 36.7% |
| 运行时库 / 加载器产物 | 25 个 | guava(26 报)、bus(33)、mixin(22)、fmlloader(60)——都不是模组 |
| `incompatible` 占声明依赖 | **5/71 = 7%** | 声明式负向边**稀疏** |
| 声明过不兼容的项目 | **3/25 = 12%** | 八个项目里只有一个 |
| 因果边 subject 可解析 | 28/60 = 46.7% | 与候选匹配率同量级 |
| `mod_ids` 字段 | **0/488** | 索引里声明了该字段，采集器从未填充 |

**四个必须记住的结论**：

1. **J1 的"替代"假设被推翻，但"补强"假设成立。**
   5/71 的密度不足以做骨架；但 7% 的高精度信号配合我们 9721 条低精度
   共现对，恰好组成"召回 + 精确"的两级结构。**声明式边是确认器，不是发现器。**
2. **匹配率 45.8% 意味着"半个整合包是不可见的"。**
   对 Pack Doctor（ROADMAP 2.2）这是硬约束：依赖检查会对一半的模组
   静默跳过。**静默跳过比报错更危险**，所以任何基于元数据的检查都必须
   显式输出"这些模组我认不出来"。
3. **`jars` 字段混入了 classpath 库，这是采集缺陷不是生态事实。**
   `JAR_RE` 抓的是栈帧后缀 `~[guava-32.1.2-jre.jar:?]`，而 1.20+ 崩溃报告
   已没有 `-- Mod List --` 段，模组和库走同一通道。任何用 `jars` 当
   "已装模组集"的下游代码都是错的——包括未来的 Pack Doctor。
4. **`mod_ids` 是死字段。** `MODID_RE`（`from mod \(...\)`）在本语料上零命中。
   要么修正则，要么删字段；留着比删掉更糟，因为它看起来像可用数据。

**这次测量的元教训**：门槛（≥40%）设得离真实值太近，导致结论
"通过但不可靠"。**下次定门槛要定在能明确分开的区间上**，
或者直接要求"区间下界 > 阈值"，而不是点估计过线。

### 3.7 残差审计（1D.2b）：机械方案的天花板在哪

匹配率 45.8% 之后，剩下的 65 个失败到底是"调参能修"还是"结构性无解"，
必须先分清再决定投入。直接探已知案例得到明确答案：

- `notenoughanimations`、`justzoom` 用**压缩写法**查询，Modrinth 返回
  **零命中**（连无关结果都没有）；换成带空格写法，`not-enough-animations`
  与 `just-zoom` **第一次就命中**，`/v2/project/...` 返回 200。
  `[事实]` `[状态: 已实测 2026-10-21]`
- 结论：失败点不在"排名太靠后"，而在**查询词根本没有词边界**。
  Modrinth 按词匹配，压缩写法不构成词。
- 于是只做了一件安全的事：命中失败后按**驼峰/字母-数字边界**再问一次
  （`XaerosWorldMap` → `xaeros world map`）。**接受规则不变**——命中项仍须
  归一化后与候选完全相等，所以它只能找到正确项目，不可能编出名字不对的匹配。
- 收益：**45.8% → 50.8%**（+6，全部是驼峰名）。已设为默认。

**剩下的 59 个分两类，都不是调参能解决的**：

| 类型 | 例子 | 需要什么 | 成本特征 |
|---|---|---|---|
| 全小写连写 | `justzoom`、`rarcompat`、`notenoughanimations` | 词典/分词器 | 一次性引入依赖，离线可跑 |
| 真别名/改名 | `appliedenergistics2`→`ae2`、`TConstruct`→`tinkers-construct` | 人工别名表 | **随模组数线性增长，永不收敛** |

这才是 1D.2b 的真正产出：**不是"提高了 5 个点"，而是"知道了 5 个点是机械
部分的全部，后面要么买依赖、要么养人工表"**。两条路都是取舍，不是技术细节，
所以停在这里等决策，而不是替用户默认开启。

还有一个字符串规则消不掉的残留风险：`--variant-retry` 可能在一组同名项目
（本体 / 移植 / 续作）里挑错。接受规则保证"名字对得上"，但不保证"挑的是本体"。

## 4. 争议点与本项目的裁决

| # | 争议 | 双方 | 本项目裁决 | 依据 |
|---|---|---|---|---|
| C1 | 规则 vs LLM | 规则可审计但覆盖窄；LLM 覆盖广但不可审计、慢、要出网 | **运行时规则，离线 LLM 辅助知识生产** | LLM4Log 的 grounding/漂移挑战 + 竞品已分占两路 |

| C3 | 模板解析 vs 结构化抽取 | 文献几乎全在做模板 | **结构化抽取**（我们绕开模板层） | 模板层是精度争议的震中；我们不需要通用性 |
| C4 | 单一分数 vs 结构化条目 | 用户想要"健康分 72" | **拒绝假精确**（VISION 已定），输出可追溯条目 | 文献的置信度表达教训 + VISION §2.2 |
| C5 | 共现即证据 | 9721 条 co_occurred 看起来"数据量大" | **降级为线索，永不单独定罪**；但也不可抛弃——声明式边实测只有 7% | 见 §3.6 |

关于 C5 补一句 `[推断]` `[置信度: 高]`：把 9721 条弱边和 82 条 `caused` 边
放在同一个 `relation` 字段里，schema 上没区分，**下游消费者迟早会误用**。
这是当前数据模型的一个真实缺陷，应在 1D 里修掉（加 `evidence_tier`）。

## 5. 目标、范围与约束（收紧版）

### 5.1 目标（一句话）

**给定一份 Minecraft 崩溃报告或日志，在离线、确定、可审计的前提下，
指出最可能的责任方与可执行的修复步骤；并在没有把握时明确说没有把握。**

三个子目标，按可验证性排序：
1. **可审计**：每条结论能追到一条 YAML 规则 + 一条证据行。
2. **可量化**：诊断率与归因准确率以区间形式公布，含样本量。
3. **可集成**：CLI / 浏览器 / GitHub Action 三种形态产出逐字节一致的文档。

### 5.2 范围（明确不做）

| 不做 | 理由 | 替代 |
|---|---|---|
| 通用日志分析 | 竞品已占且文献红海 | 只做 MC 生态 |
| 云端 LLM 诊断 | 违背离线/审计/隐私定位 | 离线 LLM 只进语料工具 |
| 健康分/单一评分 | 假精确（VISION §2.2） | 结构化 findings |
| 自动改文件/删模组 | 不可逆风险，两个版本/加载器可能同名 | 只给检查步骤 + 建议在副本实例操作 |
| 通用模板提取 | 精度震中，收益不匹配 | 结构化字段抽取 |
| Bedrock/基岩版 | 报告格式完全不同 | 明确声明不支持 |

### 5.3 约束（硬约束，不可协商）

1. **离线可运行**：诊断路径零网络。元数据抓取是**独立的离线工具**，
   产出落盘文件，诊断侧只读本地。
2. **确定性**：同输入同输出，无随机、无时间依赖（除报告自带时间戳）。
3. **单进程、低资源**：`mcd` 冷启动 < 300ms；诊断单份报告 < 200ms。
   （用户约束：仅用 ~10% 机器资源）
4. **零依赖运行时**：`mcd` 核心只用标准库 + PyYAML；不得引入 torch/transformers。
5. **浏览器形态体积上限**：Pyodide wheel 必须可接受（现状已满足，
   加 bundle 漂移守卫）。**兼容边数据不得进浏览器包**。
6. **许可证干净**：不打包第三方语料原文进发行物（`corpus/github` 原文 gitignored）。

## 6. 技术选型与优先级

### 6.1 选型（含拒绝项）

| 层 | 选择 | 拒绝 | 理由 |
|---|---|---|---|
| 诊断引擎 | YAML 规则 + 加权归因（现状） | ML 分类器 | 样本不足 + 可审计性 |
| 字段抽取 | 正则 + 结构化 section 解析（现状） | Drain/Drain3 模板 | 见 C3 |
| 兼容边来源 | **jar 清单 + Modrinth API（新增）** | 仅共现 | 见 J1 |
| 版本约束 | **Maven 区间语义（新增）** | 字符串相等 | 见 §3.5A |
| Web 运行时 | Pyodide + 预构建 wheel（现状） | 后端服务 | 离线/零成本 |
| LLM | 离线语料标注工具链（新增，人在环） | 运行时调用 | 见 C1 |
| 评测 | 确定性盲测 + 区间估计 + 蜕变测试 | LLM-as-judge | 见 §3.4 |
| 分发 | PyPI + Action + Pages（现状） | Docker（暂缓） | 拆分触发器未满足 |

### 6.2 优先级重排（对 ROADMAP 的三处修改建议）

**修改 1（已被 §3.6 实测改写）：Modrinth 元数据的用途从"负向边来源"改为"正向依赖图"。**
原判断是"它是边的最可靠来源，所以提前"。实测后改为：它确实是**最可靠**的来源，
但**量太少**（`incompatible` 仅占声明依赖的 7%），撑不起兼容图。
它真正的价值在 `required`/`optional`（64/71）——那是 **Pack Doctor（2.2）
的输入**，用于缺失前置与版本区间检查，而不是兼容图。
→ 因此 1D.2 **降级**：不删，但不再是阶段 1 的优先项，且用途重新定义为
"Pack Doctor 的元数据源 + 兼容图的确认层"。

**修改 2：把"版本回归对比"从 2.3 提前，与 Pack Doctor 同期。**
理由：§3.1 的跨数据集漂移在 MC 里表现为跨版本漂移，这是**规则失效的主要机制**，
不是运营便利功能。

**修改 3：在 1C.2（PyPI 发布）之前插入 1E（评测强化）。**
理由：发布意味着有外部用户开始引用我们的结论。没有区间估计就发布
"甩锅率 14%"，等于对外承诺一个统计上站不住的数字。**这是发布前置条件，
不是可选优化。**

## 7. 分阶段实施计划

> 每个阶段都遵循：**先量（弄明白现状）→ 再做（小步实现）→ 再验（可复现证明）**。
> 验收标准一律是"可复现的命令 + 具体数字"，不接受"看起来好了"。

### 阶段 1D：证据分级与声明式兼容边

**1D.0 现状量化（✅ 2026-10-21 完成 —— 见 §3.6）**
- 实测：匹配率 45.8%（55/120，区间跨门槛），`incompatible` 仅 5/71 = 7%。
- 结论：**门槛"数字过线但不可决策级"**，因此 1D.2 不是"可以做"，而是
  "要先解决可观测性与映射鸿沟"。

**1D.1 jar 清单解析器（✅ 2026-10-21 完成）**
- 交付：`mcd/metadata/manifest.py`，四加载器归一为
  `required`/`optional`/`incompatible` + `hard`；区间原样保留；
  自带 TOML 子集解析器并**用测试断言与 `tomllib` 逐结构相等**。
- 验收实际达成：`tests/test_manifest.py` 28 测试（原定 ≥12）。
- 未达成项如实记：夹具按文档转写，**不是 20 个真实 jar**（下载第三方二进制
  不在自动测试范围）；真实 `mods/` 验证等人指路径。

**1D.2 Modrinth 元数据抓取（已降级 + 重新定义）**
- **原计划作废**：假设声明式负向边可作骨架，实测 7% 否决该假设。
- **新用途**：正向依赖图 + 版本区间（服务 Pack Doctor），
  以及兼容图的**确认层**（co-occurrence 出候选，声明式边确认/否决）。
- **前置条件**：① 1D.3 的 tier 与"认不出"可观测性；② 1D.2b 的映射鸿沟
  （别名表 + 检索召回）。**任一未完成则不启动抓取**，否则会产出一半挂空的
  元数据，而挂空会被下游当成"没有依赖"。
- 不做：不抓文件本体、不镜像、不打包进发行物（许可证与体积双重理由）。
- 验收（**按实测下调**）：200 个模组的元数据落盘；依赖图覆盖
  `required`/`optional`；`incompatible` **不再作为验收指标**——实测只占
  7%，按它设验收等于逼实现方去凑数。改为验"声明式边被正确标为
  `evidence_tier: declared`，且未声明的不被伪造成已声明"。

**1D.3 边分级重构（1 天，含 schema 变更）**
- 做：`corpus/compat-edges.jsonl` 每条加 `evidence_tier`：
  `declared`（声明式，来自清单或 API 的 incompatible/conflicts/breaks）/
  `weak_supervision`（维护者 verdict 标签）/ `cooccurrence`（共现，
  **不可单独定罪**）。`CompatibilityClaim` 形状同步升级，
  `docs/COMPAT_EDGES.md` 写明三级语义与消费规则。
- 验收：三级分布统计；新增测试断言
  "`cooccurrence` 级边不得出现在任何归因输出中"（防止下游误用）。

**1D.4 覆盖率仪表盘（1 天）**
- 做：`tools/coverage_report.py`——按失败模式（OOM / watchdog / mixin /
  依赖缺失 / 世界数据 / 原生崩溃 / 未分类）统计语料里的诊断率与未覆盖样本，
  输出 `corpus/COVERAGE.md` + 机读 JSON。
- 验收：未覆盖报告中 Top-10 失败模式占比可读；能回答"下一个规则该写什么"。

### 阶段 1E：评测强化（1C.2 发布前置）

**1E.1 可计分样本扩容（依赖外部语料，工期不定）**
- 目标：可计分样本从 7 → **≥40**（当前区间宽到无意义）。
- 方法：继续 `harvest_corpus.py`，优先抓带明确 verdict 标签的仓库；
  对已有 7 份做双人标注算 Cohen's kappa，量化标注噪声上限。
- 失败判据：若 kappa < 0.6，先修标注规范再谈扩样本。

**1E.2 区间估计与稳定性测试（1 天）**
- 做：`blind_eval.py` 输出 Wilson 区间；新增"top-1/top-2 交换"
  稳定性测试（构造近分候选，交换顺序，断言结论不翻转）；
  新增蜕变测试（改写时间戳/玩家名/路径，断言诊断不变）。
- 验收：`corpus/BLIND_EVAL.md` 里不再出现无区间的点估计；
  三个新测试全绿。

**1E.3 离线 LLM 辅助规则候选（2 天，可选，人在环）**
- 做：`tools/suggest_rules.py`——对未覆盖语料聚类，用 LLM 生成
  **规则草稿 YAML**（只生成 `when` 条件候选与说明文字），人工审核后
  进入 `lifecycle_status: draft`。
- 硬约束：LLM 输出永不直接进 `builtin/`；必须过
  `test_rule_metadata.py` 的全部守卫；每条草稿标注生成模型与日期。
- 理由：这是数据飞轮的真实瓶颈（写规则的人工成本），
  也是 C1 裁决的落点——LLM 做知识生产，不做运行时判断。

### 阶段 2 修正（在原 ROADMAP 基础上）

- 2.1 改为"ModArtifact 填充（已在 1D.2 完成大部分）→ 补 CurseForge（可选）"
- 2.2 Pack Doctor：直接消费 1D.1 的清单 + 1D.2 的版本约束，
  实现 Maven 区间匹配；**仍不做健康分**。
- 2.3 Mod Doctor：含**版本回归对比**（原独立项，已合并）。

### 需要重点验证的四个可行性问题（按不确定性排序）

**Q1（✅ 已答，2026-10-21）：声明式边到底有多少？**
答案：**很少**。`incompatible` 占声明依赖 5/71 = 7%，25 个项目里只有 3 个
声明过任何不兼容。`mods.toml` / `fabric.mod.json` 里的 `breaks` 同理稀疏
（1D.1 只证明了"能读出来"，没证明"很多"）。
→ 原假设"声明式边可作兼容图骨架"**证伪**；J1 改为"确认层"。
→ 这条经验值得记住：**"生态里存在这个字段"和"这个字段里有很多数据"
是两件事**，前者查文档就知道，后者必须去数。

**Q2：从日志能否反推 mixin 冲突的目标类？**
这是归因能力的关键分水岭。mixin 失败日志通常含目标类名与注入点，
若能稳定抽取，就能把"两个模组改同一处"从猜测变成证据。
若抽不出，`W_MIXIN=10` 的高权重就缺乏依据，应下调。

**Q3：维护者标签能否支撑 ≥40 可计分样本？**
现在 7 份。这决定了"甩锅率"能否成为可对外说的指标。若做不到，
正确做法是**不公布这个指标**，而不是公布一个大区间。

**Q4：用户真的需要"责任方"还是只需要"下一步做什么"？**
这是产品假设，不是技术假设，文献回答不了。现有 verdict-first 设计假定前者。
若真实需求是后者，`suspect` 芯片的权重应下降，`fixes` 应上升。
**验证方式**：对 5 个真实用户做任务观察，看他们拿到诊断后第一个动作是什么。
