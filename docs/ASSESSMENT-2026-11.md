# 项目评估 · mc-crash-doctor 0.1.0（2026-11-07）

> 评估对象：`main` @ `9bc0a14`。所有数字都来自仓库内的实测产物
> （`corpus/*.json`、`tmp/assessment_*.json`）或本轮现场测量，不是估计。
> 本文回答三个问题：**做到哪了、好不好用、能不能发。**

## 0. 结论摘要

**这是一个"内部质量高、对外还差最后一公里"的专家工具。** 引擎本体扎实：
44 条规则、1000 项测试、七道门禁、真实包上把 35 条误报压到 1 条；但它还没上
PyPI，诊断正文是英文，网页依赖 CDN，覆盖率停在 75.8% 且长尾已冻结。

| 维度 | 评分 | 依据 |
|---|---|---|
| 功能完整性 | **4.5 / 5** | CLI / 库 / Action / 网页四条链路都能跑通；Pack Doctor 6/6；`--explain`、`--timeline` 齐备 |
| 准确性 | **3.5 / 5** | 语料 75.8%、盲测 72.2%；归因 mod 仓 78.3% 但加载器仓仅 60.3%；甩锅率 n=7 不可引用 |
| 易用性 | **3.5 / 5** | 一条命令 355 ms 出结论；但诊断正文英文、网页首屏 ~9 s、无 PyPI |
| 稳定性 | **4 / 5** | 1000 测试 + 七门禁全绿；真实数据刚暴露过 5 个缺陷，长期稳定性仍需时间 |
| 可维护性 | **4.5 / 5** | 模块边界清楚、docstring 解释"为什么"、0 TODO、ruff 干净；CHANGELOG 1,435 行偏重 |
| 发布就绪 | **2.5 / 5** | `publish.yml` 从未运行；pending publisher 未配置；CDN 单点 |

**一句话**：可以拿去给自己和朋友用，可以进 CI；**暂时不适合推荐给不熟悉命令行的
中文玩家**，也不适合作为"开箱即用"的产品发布宣传。

## 2. 已实现的核心功能

1. **崩溃诊断**：解析 crash report / server log / client log，识别 10 类平台
   （Forge、NeoForge、Fabric、Quilt、Bukkit 家族、混合端、代理、Bedrock 侧），
   44 条 YAML 规则给出根因、证据、2–4 步修复。
2. **归因（谁背锅）**：五类信号加权——游戏自己的 `Suspected Mods` 行 > mixin 属主 >
   栈帧模组 > jar 名 > 消息里的类名；输出分数、置信度、`--explain` 权重表。
3. **Pack Doctor（不用崩溃报告）**：读 `mods/` 每个 jar 的清单，产出四类互不混淆的
   结果——`findings` / `undecided` / `unreadable` / `not checked`；`--side` 让
   Fabric `environment` 与单侧依赖可查。
4. **四种分发**：CLI、Python 库（`mcd.diagnose`）、GitHub Action（含 pack 模式）、
   Pyodide 网页（日志不出本机）。
5. **辅助能力**：`--timeline N` 看崩溃前 N 秒、`--explain` 看归因算术、
   崩溃指纹聚类（377 组）、批量 `--dir` + `--exit-code` 做 CI 门禁。

## 3. 实测数据

### 3.1 准确性

| 指标 | 值 | 口径 |
|---|---|---|
| 平台识别 | **201/201 = 100%** | aternos 语料对上游期望值（门禁 [2] 强制） |
| 版本识别 | **176/177 = 99.4%** | 同上；唯一错例是语料自身矛盾 |
| 诊断率（全语料） | **344/454 = 75.8%** | 至少命中一条规则 |
| 诊断率（盲测） | **156/216 = 72.2% [66%, 78%]** | 从未用于写规则的那一半 |
| 归因 top-1（mod 仓） | **112/143 = 78.3% [71%, 84%]** | 方向感知，对照维护者结论 |
| 归因 top-1（加载器仓） | **44/73 = 60.3% [49%, 71%]** | 明显弱于 mod 仓，差 18pp |
| 甩锅率 | 1/7 = 14% | **n=7，不可引用**，机器标 `quotable_as_rate: false` |
| 真实整合包 | 35 条 finding → **1 条** | 355 jar 能启动的服务器包 |

解析与规则都可靠；**归因在加载器仓是短板**——那里的报告往往只有 mixin 生成的
方法名，缺少"哪个模组"的书面线索。

### 3.2 性能（本机，含解释器启动）

| 场景 | 耗时 |
|---|---|
| CLI 启动（`--version`） | 133 ms |
| 单份报告端到端 | **355 ms**（其中引擎 ~220 ms） |
| `--explain` | 355 ms（无额外成本） |
| `--timeline 60` | 150 ms |
| `--pack` 355 jar / 588 MB | **1.4 s** |
| 引擎内测（parse+规则+归因） | 中位 **16 ms**，p95 237 ms |
| 全语料 454 份 | 23.6 s |
| 网页引擎首次就绪 | ~9 s（下 ~10 MB Pyodide，之后走缓存） |

对单次使用完全够快；慢的是网页首屏，不是引擎。

### 3.3 输出噪音

| 每份报告的 finding 数 | 报告数 | 占比 |
|---|---:|---:|
| 0 | 110 | 24.2% |
| 1 | 203 | 44.7% |
| 2 | 104 | 22.9% |
| ≥3 | 37 | 8.1% |

**91.9% 的报告 ≤2 条结论**，很少出现"刷一屏"的情况。0 条的那 24.2% 里，
工具会明确说"没有规则命中，请开 issue"，不会假装诊断。

### 3.4 规则健康度

- 44 条规则全部有 fixture 证据，**0 条零证据**。
- 在 454 份 harvested 语料上触发 33 条；未触发的 11 条里，**6 条在 aternos 语料上
  真实命中**，4 条是明确标注的 `experimental`（只有合成 fixture），1 条
  （`oom.heap`）有 ground-truth 真实报告支撑。
- 使用集中度高：`crash.runtime-mod` 一条占 **188/454 = 41.4%**，其余多为长尾。
- 生命周期：40 verified + 4 experimental；4 条 experimental **不计入**发布数字。

## 4. 尚未完成与已知缺陷

### 4.1 阻塞于外部（不是工程问题）

1. **未发布到 PyPI**。`publish.yml` 从未运行过；装它只能 `pip install .` 或
   `uses: pop1022/mc-crash-doctor@main`。这是当前最大的"最后一公里"。
2. **1E.1 样本仍 n=7**。甩锅率不可引用；补 PAT 后 4 h 可扩到 ≥40。
3. **2.1 / 2.3 / 2.4 / 2.5** 卡 API 审批、持续采集与边证据质量。

### 4.2 产品缺口

4. **诊断正文是英文**。网页 UI 中英双语，但规则的 `explanation` / `fixes` 只有
   英文。对中文玩家这是体感最差的一处。
5. **覆盖率停在 75.8% 且已冻结**。110 份未覆盖里只有 2 个簇值得写规则（其中 5 份
   是"手动触发调试崩溃"，不是故障）；再写是 0.44pp/条。
6. **加载器仓归因 60.3%**，比 mod 仓低 18pp。
7. **Pack Doctor 的边界**：Forge/NeoForge 清单没有 per-mod 侧别字段，
   `wrong-side-mod` 对它们天然无效（本机四个真实包全部 `environment:"*"`，
   该检查**无真实命中样本**）；内嵌 jar 只读 mod id，不读它自己的依赖；
   Sinytra Connector 场景下 `mixed-loaders` 可能误报（未实测）。
8. **网页依赖至少一个 CDN**，且首屏 ~9 s；完全离线要自托管 ~10 MB Pyodide。
9. **语料不可分发**：`corpus/github/` 因隐私 gitignored，外部 clone 无法复现
   75.8% 与 72.2%，只能信任我们的产物。
10. **Bukkit/Spigot 插件类故障**只有平台识别，规则很少（README 已自述）。

### 4.3 工程债

11. **CHANGELOG 1,435 行**单文件，检索成本高，应归档历史版本。
12. **真实用户验证面窄**：只在本机 4 个真实包 + 6 份 ground-truth 上验证过，
    没有外部用户反馈；单人项目，无贡献者流程。
13. **无 fuzz / 属性测试**：解析器对畸形输入依赖 try/except，健壮性靠经验而非证明。
14. **本机 gate 6 会跳过 ruff**（解释器没装），需单独跑；已写进 HANDOFF 提醒。

## 5. 实际使用场景：好不好用

| 角色 | 场景 | 判断 |
|---|---|---|
| **玩家** | 游戏崩了，手上有一份 `crash-report.txt` | **好用**。一条命令 355 ms 出根因 + 2–4 步修复，不用上传日志。唯一门槛是命令行与英文正文。 |
| **服务器腐竹** | 想知道 355 个模组里有没有自相矛盾 | **有用但有限**。`--pack` 1.4 s 扫完，只报"声明层面能证明的矛盾"；包能启动不代表这些矛盾不存在，反之也不代表一定崩。 |
| **模组/整合包维护者** | 想在 CI 里拦下坏模组组合 | **可用**。Action 支持 `pack` + `fail-on`，PR 里能拦住缺前置/混用加载器；但只能 `@main`，没有版本化发布。 |
| **中文非技术用户** | 只会在网页里粘贴 | **勉强**。UI 中文，但诊断正文英文；首次等 ~9 s；网络被拦时需要看面板里列的三个 CDN 地址。 |
| **研究者/想复现的人** | 想验证 75.8% 是否可信 | **不方便**。语料不可分发，只能看产物 JSON 与命令行复算脚本。 |

## 6. 主要优点

1. **诚实**：`undecided` / `unreadable` / `not checked` 三个桶把"不知道"显式打印；
   诊断不出时明确说"没覆盖"，不编结论。
2. **快**：单份 355 ms、355 jar 1.4 s，可放进 pre-commit 或 CI 而不拖节奏。
3. **本地**：CLI 与网页都不上传日志；网页连分析都在浏览器 WASM 里跑。
4. **可审计**：`--explain` 摊开每条证据的权重，`--pack` 的每条 finding 都带
   触发的原始声明；结论可以被逐条反驳。
5. **工程纪律**：1000 项测试、七道门禁（含"文档数字必须与 JSON 一致"）、
   0 TODO、ruff 干净；真实数据暴露的缺陷当天修完并补反向对照测试。

## 7. 影响体验的问题（按严重度）

| 严重度 | 问题 | 影响 |
|---|---|---|
| 高 | 未上 PyPI | 安装门槛高，劝退非技术用户与 CI 之外的场景 |
| 高 | 诊断正文英文 | 中文用户读完中文 UI 仍要看英文解释 |
| 中 | 加载器仓归因 60.3% | Fabric/Quilt 加载器自己的崩溃，一半以上指不出模组 |
| 中 | 网页首屏 ~9 s + CDN | 弱网/被墙时体验差，虽有回退但仍可能全断 |
| 中 | 24.2% 报告无诊断 | 长尾已冻结，短期不会改善，需明确告知用户 |
| 低 | Pack Doctor 侧别检查对 Forge 无效 | 用户可能误以为"没报就是没问题" |
| 低 | CHANGELOG 过长 | 只影响贡献者，不影响用户 |

## 8. 改进建议（按投入产出排序）

| # | 建议 | 为什么值得 | 估时 |
|---|---|---|---|
| 1 | **发布 0.1.0 到 PyPI** | 解锁 `pip install`，是所有推广的前提；代码侧已就绪 | 人工 5 分钟 + 一次 dry_run |
| 2 | **诊断正文中文化**（规则加 `explanation_zh` / `fixes_zh`，渲染按 locale 选） | 中文用户体感提升最大，且不需要改引擎 | 1–2 天 |
| 3 | **补强加载器仓归因**（44/73 → 目标 55/73） | 唯一低于 70% 的核心指标，且集中在 32 份未诊断报告里 | 3–5 天 |
| 4 | **语料可复现**（下载脚本 + sha256 + 采样发布） | 让外部能验证 75.8%，这是"诚实"人设的支撑 | 1 天 |
| 5 | **网页首屏**（骨架屏 + 缓存提示 + 可选自托管 Pyodide） | 减少"打不开"的第一印象 | 1–2 天 |
| 6 | **CHANGELOG 归档**（按版本拆文件，保留近两个版本） | 降低贡献者检索成本 | 半天 |

不建议做的事：继续为长尾写规则（0.44pp/条）、用指纹聚类自动合并结论
（7 个混合簇是反例）、把甩锅率写进对外文案（n=7）。

## 9. 总体结论与适用建议

**结论：0.1.0 具备"可用"的全部工程条件，但还不具备"好卖"的对外条件。**

- **可以用**：自己排障、给朋友看报告、放进 CI 拦坏模组组合。
- **谨慎推荐**：给不熟悉命令行的中文玩家（英文正文 + 未上 PyPI 是硬门槛）。
- **暂不建议**：作为"开箱即用"的产品对外宣传；先把 PyPI 与中文正文补上，
  再用真实用户反馈决定下一轮方向。

**发布判断**：代码侧 `7/7` 门禁、`1000 passed`、真实包 1 条真阳性、网页 34/34
真机验证——**可以发 0.1.0**。唯一缺的是 PyPI 网页端的五字段配置与一次
`dry_run`，步骤在 `docs/RELEASE-0.1.0.md`。

**风险提示**：发布后对外引用数字只用 n≥30 的三项（盲测 72.2%、语料 75.8%、
mod 仓归因 78.3%）；不要引用甩锅率 1/7。覆盖率 24.2% 的空白要主动说明，
而不是等用户撞上"没有规则命中"。
