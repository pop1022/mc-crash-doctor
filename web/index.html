粘一份崩溃报告，或点「用示例试试」——示例会在 0.2 秒内给出真实报告在浏览器里跑出的结论，不用等引擎下载完。

崩在哪一行，就指向哪个模组。

同一份报告把模组的出处写在三个地方。三处对上，才敢报 97%。

  1. 01
    Mixin 归属

    一个 mixin 崩了，几乎总是它主人的锅。这是最硬的信号。

    pl:mixin:APP:create.mixins.json:Class from mod (create)
  2. 02
    模组自己的堆栈帧

    根因调用栈里第一个非原版、非加载器的类，拿去报告自己的 Mod List 里对。

    me.jellysquid.mods.lithium.common.reflection.ReflectionUtil
  3. 03
    jar 名

    帧尾的 jar 与版本直接给出构件，不用猜缩写。

    ~[some-mod-1.2.3.jar%2312!/:1.2.3]

四类死法，正好是没人管的那些。

它们不给你一条干净的异常，只留一份长得像正常关服的日志。

堆耗尽

oom.heap

“平时好好的，一 stop 就崩”不是内存泄漏，是存档时把整片区域一次性编码进内存。

95% / oom.save-time

tick 卡了 120 秒

hang.watchdog

watchdog 杀掉 JVM，报告只留下它当时卡在哪，不告诉你谁把它卡住的。

120.00 s / ServerHangWatchdog

mixin 没打上

mixin.apply-failed

两个模组改同一个类，先崩的是后来的那个，但先崩不等于先错。

oom.metaspace

加 -Xmx 一点用都没有；撑爆的是类元数据，不是堆。

村子还在原地。

崩掉的是进程，不是这个世界。存档还躺在硬盘里，日志只是它掉下来时留下的碎片。

规则是数据，不是黑盒。

一条规则就是一段 YAML：什么时候触发、为什么、怎么修。加一条不用改 Python。

  • 优先级执行 数字小的先判
  • 证据权重写在规则里 不是运行时拍的
  • 加规则只要两样 一个 YAML 加一份真实报告
看 memory-performance.yaml
mcd/rules/builtin/memory-performance.yaml16 rules
rules:
- id: oom.save-time
  title: Ran out of heap while saving the world
  severity: fatal
  priority: 5
  confidence: 0.95
  when:
    exception:
    - java\.lang\.OutOfMemoryError
    exception_msg:
    - Java heap space
    frame:
    - ChunkTaskPriorityQueueSorter|ChunkSerializer|NbtIo
    text:
    - Saving worlds|Saving chunks|stop\(\)
  explanation: The server ran out of heap while
    serialising chunks to disk.

常见问题

日志会被上传吗？

不会。引擎是编译成 WebAssembly 的 CPython，规则在标签页内跑完：没有服务器，没有统计，也没有请求带着你的日志出去。

支持哪些加载器？

Forge、NeoForge、Fabric、Quilt。服务端和客户端的报告都能读，包括只写着“Ticking entity”的那种。

和 mclo.gs 有什么不同？

它擅长加载期的报错（缺依赖、模组重复、版本不对）。这里补的是内存与性能：堆 OOM、watchdog、mixin 冲突、Metaspace，并且按三处证据给模组打分。

能离线用吗？

页面首次要拉一次 Pyodide（约 10 MB），之后诊断不出网。完全离线就用 CLI：pip install mc-crash-doctor。
