# Attribution ablation — how much of the attribution is actually ours?

> ROADMAP 1E (evaluation hardening), companion to `BLIND_EVAL.md`.
> Generated by `tools/attribution_ablation.py` on 2026-10-25 over the
> 454-fragment harvested corpus. Machine-readable twin:
> `attribution-ablation.json`. Contract pinned by
> `tests/test_attribution_signals.py`.

## The problem this measures

`triage()` gives the crash report's own `Suspected Mods:` line a weight of 12 —
the highest in the table — because the loader computes it from crash-time
classloader context, which is better evidence than anything we can infer from
text.

That makes the obvious metric worthless. "Our top-1 is in the game's list"
is **partly circular**: we are quoting the file back. It would look excellent
and prove nothing.

So the measurement is an **ablation**: delete that line from the parsed report,
re-run attribution, and ask whether the remaining evidence — mixin ownership,
mod-owned frames, jar markers, message classes — still reaches a mod id. That
is the part that is ours.

The oracle is still the loader's line, because it is the only independent
attribution available offline. It is a heuristic, not ground truth:
`minecraft` and `fabricloader` appear in it as "suspected mods" and are filtered
out here, and a report can be wrong about its own culprit. Agreement therefore
bounds **consistency**, not correctness.

## Result

n = 35 reports carrying a non-platform `Suspected Mods` entry.

The `before` column is the tool's own output from the commit preceding the new
signal, kept as `attribution-ablation-before.json` so the numbers below are
checkable rather than prose; the `after` column is `attribution-ablation.json`.

| | before | after |
|---|---|---|
| **silent** with the hint removed | **20/35 (57%)** [41%, 72%] | **3/35 (9%)** [3%, 22%] |
| answers independently | 15/35 | 32/35 |
| ... and names the same mod | 7/15 (47%) [25%, 70%] | 23/32 (72%) [55%, 84%] |
| names the same mod *with* the hint | 28/35 (80%) [64%, 90%] | 31/35 (89%) [74%, 95%] |

Read the first row as the honest headline of the pre-change tool: **on 57% of
the reports where the loader told us who it thought was at fault, removing that
sentence left us with nothing at all.** The tool was not weak on those reports;
it was silent. Presenting "top-1 matches the game" as a reliability number would
have hidden exactly that.

The `with the hint` row moved because four reports previously had *other*
evidence outvoting the loader's own line; the new signal agrees with it.

**What the frame-parser repair changed (2026-10-25).** The `after` column above
was re-measured after `mcd/parser/report.py` stopped discarding method names and
module prefixes, because that repair changes what attribution can see. Two
numbers moved and one moved the *wrong* way, so both are listed:

* silent 4 → **3**: `twilightforest#2543` can now be attributed at all.
* independently answered 31 → **32**, agreement 23/31 → **23/32**.
* agreement *with* the hint 32 → **31**: that same report is the one case where
  the new evidence overrode a hint that had been right.

`twilightforest#2543` is worth understanding rather than counting. Its
`Suspected Mods` line reads `Accessories (accessories), Minecraft (minecraft),
The Twilight Forest (twilightforest)` — three entries, and this tool scores
agreement against the *first* non-platform one. Before the repair no frames
parsed, so `accessories` won on hint weight alone. Now the trace shows
`twilightforest.client.ISTER.<init>`, which outranks it. The maintainer labelled
the issue `other mod`, so the old answer happened to match and the new one does
not. This is not "the tool started blaming an innocent mod": it reordered the
loader's own suspect list on frame evidence and lost. The lesson is about the
metric as much as the code — treating a three-entry suspect list as if only its
first entry were true is a crude oracle, and this is what that crudeness costs.

## What the silence was

Not random. 17 of the 20 silent reports were Fabric API crashes, and their only
written trace of the owner is a **mixin-generated method name**:

```
net.minecraft.registry.RegistryLoader.wrapOperation$cdi000$fabric-registry-sync-v0$wrapIsServerCall
                          real name        seed     owner mod id            rest
```

`triage()` never looked at method names, and these reports print no
`from mod (x)` marker, no mod-owned frame, and no matching jar. The owner was
sitting in the frame the whole time.

### Getting the extraction right took two corrections

**Seed anchoring.** A bare `\$([\w-]+)\$` scan over method names does not recover
mod ids, it recovers Mixin jargon. Measured on the corpus, the unanchored
version's most frequent "ids" were `bridge` (32 reports), `new` (29) and
`static` (26) — all of them structural words in `mixinextras$bridge$…` and
lambdas. Anchoring on the seed (a short alphabetic prefix plus a 3+ digit
counter: `cdi000`) collapses that noise: 114 reports, 69 distinct ids, every one
of them a real mod name.

**Depth limiting.** The first version scanned 25 frames. Its first three *hits*
included frame #12 and #14 — and one of them was Not Enough Crashes:

```
frame #12  modify$ebh000$notenoughcrashes$atTheEndOfSecondCatchBeforePrintingCrashReport
```

That mod patches the crash handler. Its mixin is present in **every report it
decorates**, which makes it perfect evidence of "this report was processed" and
worthless evidence of cause. Restricting the signal to the top 5 frames removed
both false positives and cost nothing.

### Two refinements that were measured and rejected

- **Summing per frame instead of once per mod.** Ten frames carrying the same
  mod's method is one piece of evidence, not ten. Summed, the signal reached 6×N
  and started outvoting the loader's own line: the `with the hint` agreement
  dropped from 28/35 to 25/35. Counting each (mod, signal) pair once restored it.
- **The `TRANSFORMER/<modid>@<ver>/` frame layer** (Connector / NeoForge). Also
  implemented, also measured: it added exactly **one** answer and that answer was
  wrong — `twilightforest` for a report the loader attributed to `accessories` —
  while also outvoting that report's own hint. Removed rather than tuned. It is
  the one signal in this exercise that made the tool worse in both directions,
  and it is easy to reach for because `TRANSFORMER/minecraft@…` is on nearly
  every vanilla frame.

## What this does and does not license

- It **does** show the attribution now speaks on 31 of 35 oracle-bearing reports
  and agrees with an independent computation on 74% of them.
- It **does not** replace the maintainer-verdict evaluation. The oracle is a
  heuristic; the scored sample there (`BLIND_EVAL.md`) is 7 reports against
  human labels. Neither is a substitute for the other: one has a bigger n and a
  weaker oracle, the other the reverse.
- It **does not** settle whether the seven extra blind reports the change made
  diagnosable are diagnosed *correctly*. The blind diagnosis rate moved 65% →
  68% with the change; the blame-error rate did not move, because none of those
  reports is scored.

## Known gap that was left open, and then closed

This section used to record a defect rather than an open question, so it is kept
as a record of what the measurement could not fix by itself:

> `f.cls` sometimes contains the method name, not just the class. `_parse_frame`
> splits `Class.method(args)` with a method character class that excludes `-`, so
> any method name containing a hyphen — which is **every Fabric submodule**
> (`fabric-registry-sync-v0`) — is left glued onto the class. 83 frames in 43
> reports. […] Fixing it changes `cls` across the corpus and therefore needs its
> own before/after snapshot (`tools/parser_snapshot.py`) and a gate run.

That snapshot was taken and the repair is in (2026-10-25). The defect turned out
to be three defects, not one, and the largest was not the hyphen:

| defect | frames | reports |
|---|---|---|
| trailing `[jar]` not stripped (only `~[jar]` was) | 5,432 | 148 |
| `TRANSFORMER/…/` or JPMS module prefix kept in `cls` | 16,286 | — |
| `-` in a Fabric method name glued into `cls` | 79 | 43 |

Frames parsing into `cls` + `method` went from 48,728/57,282 to **57,158/57,282**,
with `mods`, exceptions, suspected-mod lists, loaders and report kinds unchanged
on all 454 reports — the snapshot is what makes that statement checkable rather
than plausible. `tests/test_frame_parse.py` pins each row of the table above.
