# Blind evaluation — can people rely on the diagnosis?

> ROADMAP 1B.1 (blind-test system) + 1B.2 (misattribution rate),
> extended by 1E.2 (interval estimates).
> Generated by `tools/blind_eval.py --dev` on 2026-10-25 over the
> 454-fragment harvested corpus. Machine-readable twin: `blind-eval.json`
> (every ratio below also carries its `ci95` block there).
> Structural guarantees pinned by `tests/test_blind_eval.py`; the invariance
> that keeps these numbers meaningful is pinned by `tests/test_invariance.py`.

## Read this before quoting a number

Every rate in this document is followed by a **95% Wilson score interval**.
That is not decoration. The headline metric has a denominator of 7, and a
point estimate on n=7 is not a property of the tool — it is a property of
those seven reports.

The textbook normal approximation (`p ± z√(p(1−p)/n)`) is worse than useless
here: for 1/7 it returns `0.143 ± 0.26`, a lower bound below zero, which gets
clipped to "0%" and reads as *"could be perfect"*. Wilson never leaves [0, 1]
and stays sane at small n and at 0/n or n/n.

Rules applied throughout:

- **n ≥ 30** → the rate may be quoted, but only together with its interval.
- **n < 30** → it is a *count*, not a rate. Say "we documented exactly one
  failure mode", never "14%". `blind-eval.json` carries an explicit
  `ci95.quotable_as_rate` flag so this cannot be lost downstream.

## Method

**Split** (deterministic, reproducible): every report cited in a rule's
`provenance.fixtures` is forced into the **dev** set — a rule is never
"blind-tested" on the report that motivated it. Remaining reports are split
by `sha256("repo/issue") % 10 < 5` → **blind 218 / dev 236**.

**Attribution scoring is direction-aware**, driven by the maintainer's
weak-supervision verdict (harvested from issue labels):

| verdict | what top-1 suspect SHOULD be | scoring |
|---|---|---|
| `bug_in_this_mod` | the repo's own mod | hit = correct; other mod = **blame error** |
| `root_cause_elsewhere` | some OTHER mod | other mod = correct; repo's mod = **blame error** |
| `known_issue` / `outdated_version` | ambiguous direction | reported, not scored |
| no verdict / `user_error_or_config` / `meta` | n/a | diagnosis rate only |

Loader/library repos (fabric-loader, fabric-api, quilt-loader) are
diagnosis-rate-only: "blame the repo's mod" is meaningless there.

**Tie-break** (fixed in 1E.2): equal scores are ordered by mod id, not by the
order the mod appears in the report. Before the fix, two reports of the same
two-mod interaction written in opposite order could name different top
suspects — which made "top-1 is the repo's mod" partly an artefact of prose
ordering. See `tests/test_invariance.py`.

## Results (blind set, n=218)

| metric | value | 95% CI | quotable as a rate? |
|---|---|---|---|
| parse errors | 0 | — | yes (it is a count) |
| diagnosed (≥1 finding) | 155/218 (71%) | [65%, 77%] | yes |
| root cause extracted | 217/218 (99%) | [97%, 100%] | yes |
| mod repos diagnosed | 112/143 (78%) | [71%, 84%] | yes |
| loader repos diagnosed | 43/75 (57%) | [46%, 68%] | yes |
| **blame-error rate** | **1/7 scored** | **[3%, 51%]** | **NO — n=7** |

The blame-error row is the one that matters for trust, and it is the one we
cannot yet quote as a rate: with 1 error in 7 scored reports, the same data is
consistent with a 3% error rate and with a 51% error rate. The honest sentence
is **"we found and documented exactly one failure mode out of seven scorable
reports"**, and that is what the roadmap's 1B.2 claim rests on.

**Dev comparison** (dev reports motivated the rules, so a *better* dev number
would prove nothing): 182/236 (77%) diagnosed [71%, 82%], 1/6 blame errors
[3%, 56%].

The blind and dev intervals overlap almost completely — which means this
comparison has essentially **no power**: it can neither confirm nor rule out
overfitting. Earlier revisions of this document called that "no significant
overfitting"; that was an over-reading of two intervals on denominators of 7
and 6, and is retracted.

**Why the diagnosis rate moved from 65% to 71% between revisions.** Two changes,
both of which only ever *added* reachable evidence:

1. 65% → 68%: attribution gained one signal (the owner baked into Fabric's
   mixin-generated method names; see `ATTRIBUTION_ABLATION.md`), so seven more
   blind reports now reach a mod id.
2. 68% → 71%: the frame parser was fixed (`mcd/parser/report.py`, see the
   2026-10-25 CHANGELOG entry). It had been throwing away the method and line
   number on 5,432 frames across 148 reports, and keeping a `TRANSFORMER/…` or
   JPMS module prefix on 16,286 more — so `_modid_from_class` could not resolve
   those frames at all. Seven further blind reports now reach a mod id.

The scored blame-error rate did **not** move in either revision: 1/7 before,
1/7 after. That distinction matters — both changes made the tool *speak* on more
reports, and the evidence that it speaks *correctly* is the oracle agreement in
`ATTRIBUTION_ABLATION.md`, not a better number here.

One report did change its top-1 in step 2, and it is worth naming because it is
the shape of the failure this kind of repair can cause:
`TeamTwilight/twilightforest#2543` (maintainer label `other mod`). Its `Suspected
Mods` line lists three mods — `accessories`, `minecraft`, `twilightforest` — and
the old parser saw no frames, so the loader's *first* entry won on the hint
weight alone. The repaired parser sees `twilightforest.client.ISTER.<init>`, and
`twilightforest` now outranks `accessories` — i.e. we reordered the loader's own
list using frame evidence, and landed on the entry the maintainer ruled out.
It is not in the scored set (no verdict), so the 1/7 is unaffected, but it is a
concrete example of "more evidence can also disagree with a correct hint".

By verdict (diagnosis rate, all intervals wide):

| verdict | diagnosed | 95% CI |
|---|---|---|
| `known_issue` | 5/5 | [57%, 100%] |
| `root_cause_elsewhere` | 3/3 | [44%, 100%] |
| `outdated_version` | 2/2 | [34%, 100%] |
| `meta` | 2/2 | [34%, 100%] |
| `not_a_bug` | 1/1 | [21%, 100%] |
| `bug_in_this_mod` | 3/4 | [30%, 95%] |
| `user_error_or_config` | 28/42 (67%) | [52%, 79%] |
| no verdict | 111/159 (70%) | [62%, 76%] |

Only the last two strata have denominators worth a percentage at all. The
`1/1` and `2/2` rows are listed for completeness; they carry no information
beyond "the rule fired".

## The one blame error — a documented attribution limit

**Mekanism/8455**: maintainer labels `interaction` + `Not Mekanism`
(verdict `root_cause_elsewhere`), but every stack frame is
`mekanism.api.*` / `mekanism.common.*` (a ClassCastException in
BasicChemicalTank). Our attribution says mekanism; the maintainer says the
real cause is the **Sinytra Connector** compatibility layer.

This is not a coding bug — it is the known limit of stack-frame attribution:
**bytecode-level mod interaction is invisible in the trace**. The report
even opens with Connector's "verify issues are not caused by Connector"
disclaimer. Candidate future signals: Connector present in Mod List +
`TRANSFORMER/` frames + maintainer `interaction` label pattern.

Pinned by `test_direction_aware_scoring_on_known_samples` so any change
(improvement included) is a deliberate, reviewed act.

Correct-direction external attributions (for contrast): TinkersConstruct
#5379 → mantle ✓, #5590 → mekanismtools ✓.

Note the other three `bug_in_this_mod` reports: none was *misattributed*, all
three got `no pick` (attribution produced nothing to blame). "No pick" is a
different failure from "wrong pick" — it costs the user help but it does not
send them to the wrong mod's issue tracker.

## Honest limitations

1. **Report-level blind, corpus-level not**: rule *wording* was informed by
   corpus-wide blind-spot clustering. These numbers measure generalisation
   to unseen reports, not prospective validity. The genuinely prospective
   blind set grows automatically with every future re-harvest (hash-based
   split).
2. **Scored sample is tiny** (7 reports with unambiguous direction
   verdicts). See the interval table above: [3%, 51%] is not a rate yet.
   Fixing this is ROADMAP 1E.1 (harvest to ≥40 scorable reports), which is
   blocked on GitHub API quota.
3. **Weak labels**: maintainer labels are ground-ish truth, not adjudicated
   root cause.
4. **Positions and identity were not always neutral**: the tie-break fix
   (1E.2②) changed results only where scores were exactly equal; the
   metamorphic tests (1E.2③) show the remaining diagnosis is unaffected by
   timestamps, player names and install paths on the sampled reports. That is
   evidence, not proof — the sample is 6 reports.
