# Blind evaluation — can people rely on the diagnosis?

> ROADMAP 1B.1 (blind-test system) + 1B.2 (misattribution rate).
> Generated by `tools/blind_eval.py --dev` on 2026-09-24 over the
> 454-fragment harvested corpus. Machine-readable twin: `blind-eval.json`.
> Structural guarantees pinned by `tests/test_blind_eval.py`.

## Method

**Split** (deterministic, reproducible): every report cited in a rule's
`provenance.fixtures` is forced into the **dev** set — a rule is never
"blind-tested" on the report that motivated it. Remaining reports are split
by `sha256("repo/issue") % 10 < 5` → **blind 218 / dev 236**.

**Attribution scoring is direction-aware**, driven by the maintainer's
weak-supervision verdict (harvested from issue labels):

| verdict | what top-1 suspect SHOULD be | scoring |
|---|---|---|
| `bug_in_this_mod` | the repo's own mod | hit = correct; other mod = **blame error** |
| `root_cause_elsewhere` | some OTHER mod | other mod = correct; repo's mod = **blame error** |
| `known_issue` / `outdated_version` | ambiguous direction | reported, not scored |
| no verdict / `user_error_or_config` / `meta` | n/a | diagnosis rate only |

Loader/library repos (fabric-loader, fabric-api, quilt-loader) are
diagnosis-rate-only: "blame the repo's mod" is meaningless there.

## Results (blind set, n=218)

| metric | value |
|---|---|
| parse errors | 0 |
| diagnosed (≥1 finding) | **141/218 (65%)** |
| root cause extracted | 217/218 (100%) |
| mod repos diagnosed | 102/143 (71%) |
| loader repos diagnosed | 39/75 (52%) |
| **blame-error rate** | **1/7 scored (14%)** |

Dev-set comparison: 69% diagnosed, 1/6 blame errors (17%) — blind and dev
are within noise of each other, i.e. **no significant overfitting to the
reports that motivated the rules**.

By verdict (diagnosis rate): `known_issue` 5/5 · `root_cause_elsewhere` 3/3 ·
`outdated_version` 2/2 · `meta` 2/2 · `not_a_bug` 1/1 ·
`bug_in_this_mod` 2/4 · `user_error_or_config` 26/42 · no verdict 100/159.

## The one blame error — a documented attribution limit

**Mekanism/8455**: maintainer labels `interaction` + `Not Mekanism`
(verdict `root_cause_elsewhere`), but every stack frame is
`mekanism.api.*` / `mekanism.common.*` (a ClassCastException in
BasicChemicalTank). Our attribution says mekanism; the maintainer says the
real cause is the **Sinytra Connector** compatibility layer.

This is not a coding bug — it is the known limit of stack-frame attribution:
**bytecode-level mod interaction is invisible in the trace**. The report
even opens with Connector's "verify issues are not caused by Connector"
disclaimer. Candidate future signals: Connector present in Mod List +
`TRANSFORMER/` frames + maintainer `interaction` label pattern.

Pinned by `test_direction_aware_scoring_on_known_samples` so any change
(improvement included) is a deliberate, reviewed act.

Correct-direction external attributions (for contrast): TinkersConstruct
#5379 → mantle ✓, #5590 → mekanismtools ✓.

## Honest limitations

1. **Report-level blind, corpus-level not**: rule *wording* was informed by
   corpus-wide blind-spot clustering. These numbers measure generalisation
   to unseen reports, not prospective validity. The genuinely prospective
   blind set grows automatically with every future re-harvest (hash-based
   split).
2. **Scored sample is tiny** (7 reports with unambiguous direction
   verdicts). The 14% blame-error rate has huge confidence intervals;
   treat it as "we found and documented exactly one failure mode", not as
   a stable statistic. More labelled verdicts (125 exist corpus-wide; only
   mod-repo crash-type ones are scorable) will tighten it.
3. **Weak labels**: maintainer labels are ground-ish truth, not adjudicated
   root cause.
